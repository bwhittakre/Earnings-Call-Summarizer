Phase 3b was specified as two things: schedule the next quarter when a call COMPLETEs, and re-verify the date at T-7. Building either as a separate trigger turned out to be the wrong shape.

EVIDENCE AGAINST A COMPLETE HOOK. Quartr publishes the next quarter long before the current one is scored. On disk right now: NVDA FY2027-Q2 is complete AND FY2027-Q3 is already published; TXN and CTSH completed FY2026-Q2 and already have FY2026-Q3; all 45 onboarded tickers have a future manifest, furthest 99 days out. A COMPLETE-triggered lookup would therefore be redundant machinery for an outcome the sweep already produces -- and strictly worse, because it fires ONCE at a moment Quartr may not yet have the date, with no retry. The periodic sweep retries daily and is self-healing. Same argument retires an explicit T-7 check: a daily sweep re-verifies every day, which dominates checking once at T-7.

So Phase 3b reduced to making the sweep's re-verification CORRECT and VISIBLE.

BUG FOUND AND FIXED (state guard). discover() has two update paths. The reissued-ID path (_absorb_reschedule, Phase 3a) is gated on RESCHEDULABLE_STATES, but the same-ID path had NO state guard -- and same-ID-with-corrected-times is the COMMON case, because Quartr firms up its estimates in place rather than minting a new ID. A late correction therefore rewrote the recorded call_at of a quarter Roz had ALREADY SCORED, so the record no longer said when the call actually happened. Confirmed by test before fixing: the COMPLETE case failed, the pre-call case passed. Both paths now share the RESCHEDULABLE_STATES gate and the skip is logged.

VISIBILITY. Re-verifying a date is worthless if the answer is invisible. PublishResult now carries call_at + previous_call_at with a `rescheduled` property; publish_calendar reads the manifest before overwriting and logs SCHEDULE CHANGED; the CLI prints every move and, via --verify-within-days (default 7), promotes a move on an IMMINENT call into the failures list so it reaches host health. That is the T-7 signal, expressed as an attention window over a continuous check rather than a one-shot.

A corrupt existing manifest reads as 'nothing published' -- change detection is reporting and must never be the reason a sweep fails.

VERIFIED ON REAL DATA, not just unit tests: replaying the live Quartr rows for AAPL into a temp events dir, a fresh publish reported no change (no false positive), a manifest rewound 3 days was detected and logged, and the re-sweep corrected it back to the true 2026-10-29T20:00:00Z. Live manifests untouched.

THE CYCLE IS NOW ACTUALLY RUNNING. Monitor DB shows 5 events auto-armed with manual_override=0 sitting in awaiting_release: AVGO (today), ADBE (+8d), ORCL (+9d), MU and ACN (+28d). For context, forensics earlier in this workstream found only ONE call (OPAL) had ever armed automatically in five weeks. Only 5 of 48 manifests are armed because discovery uses a 30-day lookahead; the rest arm as they come into range, which is correct.

Also confirmed the publish path is not a dead end: the sweep writes to earnings-scraper-main/earnings-scraper-main/inbox/events, which looks like the retired scraper but is the legacy-but-live inbox location and is bind-mounted into roz-monitor-1. The container sees all 48.

Suite 854 passed (was 849; +5 tests). Session ccf4b6 debug instrumentation stripped: _debug_probe.py deleted, probes removed from eligibility.py / providers.py / service.py, log files removed.

REMAINING AND NOW BINDING: the sweep is still not on a timer. Every guarantee above is conditional on it running periodically; nothing re-verifies while it is invoked by hand.
