DashboardData.operational_alerts built its verdict from injected records but then also called load_host_health(resolve_host_health_path()), whose fallback is Path.cwd()/host_quartr/health/last_run.json. So a pure classifier silently depended on where the process started AND on whether the host automation had ever run.

It surfaced the first time 'calendar --source mcp' actually wrote host_quartr/health/last_run.json: test_dashboard_classifies_stuck_and_repeated_failures started failing with an extra host_feed_stale alert. The test's now= is 2026-09-24 while the file was stamped 2026-09-02, so relative to the test clock the real feed read as 22 days stale.

This was latent, not caused by the Quartr work -- it would have broken for anyone the moment the host automation ran for real, which is the entire point of Phase 2. Confirmed by bisection: the test passes with the file moved aside and fails with it restored.

Fix: operational_alerts now takes host_health_path and threads it into resolve_host_health_path(explicit=...); the test passes a tmp path that does not exist so it asserts pure classification. Suite green at 830 with the real host feed present.

Watch for the same shape elsewhere: host_feed_status() in the same module still resolves from cwd, and Path('host_quartr/worklists/due_sweep.json') there is a bare relative path.
