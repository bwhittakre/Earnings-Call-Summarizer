Two separate failures made memory `health()` (and any tool that shells out to git) time out with -32001 on 2026-09-02. Both are patched in `C:\Users\BobbyWhittaker\AppData\Local\angelo-venv\Lib\site-packages\sitecustomize.py` (auto-imported by every venv python; survives `angelo update`; delete the file to revert).

1. Windows stdio deadlock (morning). The MCP server keeps a thread blocked in ReadFile() on its stdin pipe. Any child spawned with default `stdin=None` inherits that pipe; git.exe's C runtime probes std handles at startup and freezes in the kernel (0 CPU, unkillable) until Cursor sends the next RPC message, which it never does while waiting for the reply. Proof: sending any `ping` to the server's stdin unblocked `health()` instantly. Fix: on win32, when the process's own stdin is a pipe, `subprocess.Popen.__init__` defaults `stdin=DEVNULL` for children whose caller left stdin unspecified. Disable with `ANGELO_NO_STDIN_GUARD=1`. Upstream fix would be `stdin=subprocess.DEVNULL` at the subprocess call sites in memory/server.py, memory/git_state.py and the coordinator/zettelkasten equivalents.

2. Stand-down churn in the Cursor Agents shell (afternoon). Cursor's 'Cursor Agents' window hosts workspaces as tabs; the shell itself has no folder, so the user-global angelo plugin launches there with an empty `${workspaceFolder}`, `workspace_root()` falls back to $HOME, no markers -> `stand_down(mode=exit)`. Cursor logs 'Connection closed', flips the PROFILE-WIDE plugin status to error, and tears down + respawns every other tab's connection ('stopped connection' every 1-2 min). Tool calls then fail 'Timed out waiting for connection' / 'Not connected' even though the real repo's server booted fine and never received the call. Fix: `os.environ.setdefault('ANGELO_STANDDOWN_MODE', 'serve_empty')` so the folder-less shell keeps a bare tool-less server connected instead of exiting. This is the switch mcp_common/workspace.py documents as 'UNVERIFIED how Cursor renders an immediate exit' - now verified: exit mode is unusable under the Agents shell.

Diagnostic path that worked: `%APPDATA%\Cursor\logs\<session>\mcp-server-plugin-angelo-memory.log` is the server's stderr plus Cursor's FSM transitions; look for 'standing down', 'stopped connection', and whether a CallToolRequest ever arrived. Also: after a server process is killed, Cursor parks the client in `closed` and does NOT respawn - a 'Developer: Reload Window' (or plugin toggle) is required. Note the repo's `.cursor/mcp.json` and the nested earnings-scraper-main `.cursor/` plus a Temp worktree tab each launch their own server set; that multiplies processes but was not the cause of either failure.
